# Data Dictionary: Batch 0.2: Attendance & Meetings

Extracted directly from the working demo code. One important gap is flagged up front before the tables, since it affects how this batch should be read.

---

## Flag: "automatic recurring sessions" was never actually built in the demo: now resolved

The Attendance page displays this line under the weekly schedule: *"Recurring sessions above are generated automatically each week from this schedule."*

That line was **not backed by real logic in the demo**. Checking the actual code confirmed:
- All 11 sessions in the demo are hand-written mock data, not generated by anything.
- The only session-creation function (`createSession`) is a manual form behind the "New session" button , there was no scheduler, no date-based trigger, nothing that ran weekly.

**This is now resolved** , see the confirmed decision below: the real system will implement this properly with a scheduled backend job, so the on-screen claim becomes true rather than aspirational.

## Table: `meeting_types`

| Field | Type | Required | Notes |
|---|---|---|---|
| id | Text/Slug (PK) | Yes | Demo uses short slugs like `fri-worship`, `mon-bs` |
| name | Text | Yes | e.g. "Friday Worship Service" |
| day | Text | No | e.g. "Friday". Occasional meetings show `,` |
| frequency | Enum | Yes | `weekly` / `occasional`. **Currently just a display label** , see flag above; it has no scheduling effect in the demo. |
| detail_level | Enum | Yes | `detailed` / `simple` , controls which attendance categories apply (see below) |
| monthly_target | Integer | No | Nullable. Only set for Friday Worship (150) and Monday Bible Study (60) in the demo, but not restricted to weekly meetings , occasional meetings can carry a target too. Feeds the Goals module directly , this is a real cross-module relationship, not just display. |

**Business rule confirmed:** `detail_level` determines which headcount fields are shown when recording attendance for that meeting:
- `detailed` → Men, Women, Youth Boys, Youth Girls, Children Boys, Children Girls (6 categories)
- `simple` → Men, Women only (2 categories)

This is enforced in the UI (the session form only renders the relevant fields for that meeting's level), so the same rule must be enforced server-side too , not just trusted from the frontend.

## Table: `attendance_sessions`

| Field | Type | Required | Notes |
|---|---|---|---|
| id | Integer (PK) | Yes | |
| meeting_type_id | Text (FK → meeting_types.id) | Yes | |
| date | Date | Yes | |
| location_id | Text (FK → locations.id) | Yes | |
| mode | Enum | Yes | `in-person` / `online` |
| status | Enum | Yes | `pending` / `filled`. A session starts `pending` (headcounts empty) and becomes `filled` the moment someone saves numbers into it. |
| track_named | Boolean | Yes | Defaults false. Whether named attendance was used for this session (see below). |

**Headcounts:** stored per category, one column per category key (`men`, `women`, `youth_boys`, `youth_girls`, `children_boys`, `children_girls`), each nullable/zero depending on the meeting's detail level. A `simple` meeting will only ever populate `men` and `women`.

**Business rule confirmed: headcount is always the source of truth.** Named attendance (below) is explicitly supplementary , the UI tells the user this directly ("Headcounts above remain the source of truth for attendance totals; this list is supplementary"). The two are not required to reconcile against each other.

## Table: `attendance_session_members` (named attendance)

A join table , the demo stores this as a simple array of member IDs per session, which becomes a proper join table in the real schema.

| Field | Type | Required | Notes |
|---|---|---|---|
| session_id | Integer (FK → attendance_sessions.id) | Yes | |
| member_id | Integer (FK → members.id) | Yes | |

**Business rules confirmed:**
- Only shown/used when `track_named` is true for that session.
- The member list has no location restriction , any member, from any location, can be checked off at any session. This was changed from the demo's stricter location-matching behavior; the search box is relied on to narrow the list quickly.
- This is optional per session , most sessions in the demo never use it; only one seeded example does.

---

## Relationship summary

- One Meeting Type → many Attendance Sessions
- One Attendance Session → many Members (via the named-attendance join table), optional
- Attendance Sessions reference Locations (already established as its own table from Batch 0.1)
- `meeting_types.monthly_target` is read directly by the Goals module (Friday Worship and Monday Bible Study goals pull their target from here, not a separately duplicated number)

---

## Decisions confirmed

1. **Recurring session generation is fully automatic.** A scheduled backend job creates the upcoming `pending` session for every `weekly` meeting type on its own, with no staff action required , matching the fixed, known weekly schedule. This replaces the demo's non-functional text claim with a real mechanism (option (a) from the original three).
2. **Monthly targets can apply to occasional meetings too**, not just weekly ones. `monthly_target` on `meeting_types` is not restricted by frequency.
3. **Named attendance has no location restriction.** The member checklist for any session shows all members regardless of location , a Qatar-based member visiting a Bahrain service can be checked off. The existing search box handles narrowing the list down quickly.

Batch 0.2 is now fully resolved.
